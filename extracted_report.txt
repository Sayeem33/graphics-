CHAPTER I
Introduction and Project Scope
1.1 Introduction
This project implements an interactive three-dimensional Solar System in C++20 and OpenGL 3.3 Core.
It contains the Sun, all eight planets, the Moon, and the four Galilean moons included in the scene.
The application combines real-time rasterization, texture mapping, selectable point, directional, and
spot illumination, several shading modes, Keplerian orbital motion, interactive navigation, geometry
inspection, and an optional analytical ray tracer. The goal is not a literal scale model; it is a technically
correct and visually readable graphics demonstration in which the essential equations and transformations
remain visible in the source code.
Figure 1.1: Closer raster overview of the inner system, at camera distance 46 and elevation 55◦. The Sun and inner
planets are readable here; the outer planets remain in the scene but are outside this close framing.
1.2 Objectives and Achieved Scope
The objectives are reusable indexed geometry, axial/orbital animation, model–view–projection and normal
transforms, three raster shading and light types, texture and shell passes, interactive navigation and vertex
inspection, and analytical ray visibility with shadows and one reflection. Each is explained below using
the actual source equations and screenshots.
1.3 Software Architecture
The CPU owns scene records, orbital time, camera state, object selection, texture loading, and draw
submission. OpenGL vertex shaders transform mesh vertices; fragment shaders evaluate surface color
and raster lighting. The optional ray-tracing mode instead uploads analytical sphere and ring records
and reconstructs one camera ray per pixel. GLFW creates the window and input callbacks, GLAD loads
OpenGL entry points, GLM supplies vector and matrix mathematics, stb loads and writes images, and
Dear ImGui implements the control and inspector panels.
Figure 1.2 separates CPU scene work from the two GPU visibility methods. Both branches share the same
simulation and camera. The ray branch does not receive the raster textures, orbit-line buffers, star-point
buffer, or atmosphere shells.

3.3 OrbitPath: Sampled Curves, Not Physical Objects
SolarSystemSimulation::orbitPoints() returns 320 world-space positions for each of eight plan-
etary paths. It substitutes E j = 2π j/320 into Eqs. (2.4)–(2.6). These are uniformly spaced parameter
samples, not equal-time positions in realistic mode.
OrbitPath uploads positions to a VAO/VBO, with no normals, UVs, or element buffer. Its draw call
is glDrawArrays(GL_LINE_LOOP,0,320); the primitive closes the final-to-first segment automatically.
All paths together store 2,560 positions. The path vertices are already oriented world coordinates, so
orbit.vert uses PV p without a model matrix. These path samples are for display only: orbital motion
is evaluated analytically each frame, not by moving through the line vertices.
The normal interactive path color is 0.45Cbody + 0.55(0.72,0.72,0.72), with alpha 0.30. The isolated
report capture increase line opacity/width only for legibility, as its caption notes. Depth testing stays
active, depth writes are temporarily disabled, and ordinary alpha blending composites the lines. Changing
orbit mode rebuilds the path buffers so the curves agree with the selected position model. Satellite orbit
paths are not implemented, and no orbit lines are composited into ray-tracing mode.
Figure 3.2: Eight realistic orbit paths isolated from bodies/stars; distance 230, elevation 70◦. For print legibility
only, this diagnostic capture uses alpha 0.75 and 2-pixel lines; normal paths use alpha 0.30.

4.3 Texture and Specialized Passes
4.3.1 Texture Loading, UV Sampling and Procedural Fallback
Texture2D loads JPEG files using stb, selects the appropriate channel format, uploads the pixels,
generates mipmaps, repeats longitude u, clamps polar v to the edge, and uses trilinear minification
and linear magnification filtering. Day/night RGB maps use an sRGB internal format, so OpenGL
decodes them when sampled; the cloud map is loaded as linear data. Texture units are bound to the
sampler uniforms, and interpolated UVs select pixels. No normal map, displacement map or geometry
displacement is used.
When surface maps are disabled, surfaceColor() synthesizes object-space patterns from value noise
and five-octave fractal noise (initial amplitude 0.52, frequency multiplier 2.03, amplitude multiplier 0.48).
Style branches imitate rocky terrain, clouds, continents, gas bands, and storms. These patterns change
color, not the sphere’s shape. The Sun always uses its procedural animated emission because it has no
downloaded day map. Its boiling-noise coordinate includes (0.07t,−0.045t,0.03t) with simulation time
t.

CHAPTER V
Rasterization, Ray Tracing, and Interaction
5.1 Rasterization Pipeline
The raster renderer clears color and depth buffers, draws the star field and orbit curves, submits opaque
spheres, draws Earth clouds and Saturn’s ring with blending, adds atmosphere and glow shells, then
optional geometry overlays, labels, and the interface. Depth testing uses GL_LEQUAL; back-face culling
removes back-facing surfaces of closed meshes. Transparent rings are deliberately two-sided. OpenGL
converts clip-space triangles to fragments, while the fragment shader determines the final material and
light response [1].
The shared sphere is transformed separately for each object: the same local vertex produces different
world positions through a different M. The normal is transformed with Eq. (2.12), not PVM. World
position, world normal and UV are interpolated to fragments; normals are normalized again before
lighting. No geometry or tessellation shader is used.
Standard transparent passes use Cout = αCsrc +(1−α)Cdst. Stars and halos instead use additive Cout =
αCsrc +Cdst. Depth writes are temporarily disabled for paths and transparent/overlay passes, preventing
their depth values from hiding later surfaces. This simple fixed draw order is not order-independent
transparency.

GL_MULTISAMPLE. This is a requested context configuration, not a measured guarantee that every GPU
provides exactly four samples. It primarily smooths geometric edges; it does not make the analytical ray
shader trace four rays per pixel.

5.3 Selection and Interaction
Picking is implemented for the Sun and eight planets only. pickBodyVertex() receives their nine
bodyModels; it does not receive satellite models or Saturn’s ring. It rescales window cursor coordinates
to framebuffer pixels before converting to NDC, which matters on high-DPI displays. Inverting PV at
NDC depths −1 and +1, followed by homogeneous divides, supplies near/far world points and the ray
direction. Its origin is the eye.
The picker first finds the closest positive intersection with those body spheres. It then loops over the
561-vertex inspection sphere on that one body, transforms each candidate by M, rejects candidates with
Nworld ·normalize(ceye −pworld) ≤0, and rejects points behind the eye or outside the NDC frustum. The
remaining candidate with the smallest squared pixel distance to the cursor is selected. There is no vertex-
distance acceptance threshold. The 5-pixel limit in main.cpp distinguishes a click from accumulated
camera-drag movement; it is not a vertex-picking radius.
The inspector reports the selected local/world position, local/world normal, UV, projected pixel/depth,
and M, V, P. Its selected record is refreshed while bodies move. Wireframe and vertex overlays use the
inspection sphere, so the reported vertex index belongs to that 561-vertex grid, not the production sphere.
Visibility filtering is geometric front-side/frustum filtering, not a read-back of a per-pixel object-ID buffer.

CHAPTER VI
Implementation, Results, and Verification
6.1 Implementation Environment
The project is built with CMake and C++20 using the Windows x64 preset. Its principal dependencies are
GLFW, GLAD, GLM, stb image/image-write, and Dear ImGui. The present preset names the installed
Visual Studio generator and uses the adjacent vcpkg toolchain; VS Code can act as the editor and CMake
front end without replacing that C++ compiler toolchain.
Assets remain under assets/textures.
The actual CMake file embeds the source shader, as-
set, and output directories using SOLAR_SYSTEM_SHADER_DIR, SOLAR_SYSTEM_ASSET_DIR, and
SOLAR_SYSTEM_OUTPUT_DIR. It does not copy shaders/textures beside the executable. The current
binary therefore depends on those source-tree resource paths; a relocatable release would need an explicit
packaging change.
Code navigation. main.cpp coordinates input, uniforms and draw passes; SolarSystem.cpp owns or-
bital positions and model matrices; Camera.cpp supplies navigation and view matrices; Meshes.cpp con-
structs geometry and buffers. Shader.cpp compiles/links programs and uploads uniforms, Texture.cpp
uploads filtered images, VertexPicker.cpp selects a body/vertex, and RayTracer.cpp uploads the
analytical scene. Body, ring, star and ray shader functions are identified in their respective sections.
6.2 Automated and Visual Verification
self-test renders four hidden-context frames: Enhanced/point, Gouraud/directional, Phong/spot
with geometry overlays and centered picking, then ray tracing. It checks Earth’s display radius/period,
Neptune’s distance above 100, relative period ordering, and a four-point Mercury orbit with aphelion
farther than perihelion. Each frame checks glGetError(); picking must select the centered Sun, and the
ray frame’s center RGB sum must be at least 24. The current build passes. These are smoke checks, not
exhaustive intersection/image tests, framebuffer-completeness checks or a frame-rate benchmark.

19
capture-report produces 36 RGB PNGs using paused orbital time, fixed scene/camera settings, one
warm-up frame per capture, and row reversal after framebuffer readback. The report selects and crops
these images losslessly; original captures are preserved. Portraits face the sunlit hemisphere under the
original Sun point source, not an added fill light. Diagnostic path opacity/width changes are stated in the
caption. The star detail is a 160-by-160 crop. Seeded geometry is repeatable, but wall-clock star twinkle
and GPU rasterization can vary pixels; captures are not bitwise deterministic or fabricated.
6.3 Limitations and Future Work
The AU distance map and body radii are deliberately hybrid-scaled; a literal astronomical scale would
make planets too small or too distant for one interactive view. Planet spins use presentation periods and
fixed axial tilts rather than real spin-period ratios. Planetary initial phases and orbital-element conventions
are not a date-based ephemeris. Satellites use local demonstration periods and circular offsets, and equal
spin/orbit periods do not enforce a tidally locked face. The ray tracer uses analytical colors instead of
full raster textures and shells. Transparency, shadows and atmospheres are stylized approximations as
detailed above.
Relevant future work includes a parent-facing satellite orientation frame, calendar/epoch-based orbital
state, more satellites and moon paths, textured ray hits using inverse body transforms, a BVH for larger ray
scenes, finite-area-light soft shadows, ray-tracing supersampling or post-process anti-aliasing, physically
based materials, atmosphere scattering, improved transparent-pass ordering, and level-of-detail meshes.
Ordinary raster MSAA is already requested; adding anti-aliasing from scratch is therefore not an accurate
description of the remaining work.
CHAPTER VII
Conclusion
The project demonstrates how reusable vertices become positioned objects through model, view, pro-
jection, orbital, and hierarchical transformations; how normals, textures, illumination, and interpolation
determine raster appearance; and how analytical rays provide a different visibility solution. The realistic
Keplerian orbit update improves spacing and speed behavior while retaining compressed distances and
presentation-scale radii. Separate screenshots expose each included celestial object’s parameters, and
dedicated ring, orbit-path and star-field evidence explains the non-spherical geometry. The source-audited
equations, fixed-state captures and clearly scoped smoke test support assessment and extension without
overstating scientific fidelity or test coverage.
